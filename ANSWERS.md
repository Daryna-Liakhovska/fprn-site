# ANSWERS.md — Частина 2: програми академічного обміну

Застосунок: `exchange`. Усі зміни структури й даних — тільки через міграції:

| Міграція | Що робить | Тип |
|---|---|---|
| `0001_initial` | Модель «Програма обміну» рівно з полями: id, університет, мови навчання, кількість місць (текст), дедлайн (дата), опис | схема |
| `0002_seed_programs` | Переносить таблицю деканату «як є» | `RunSQL` |
| `0003_exchangeprogram_country` | Додає поле «країна» | схема |
| `0004_split_university_country` | Розділяє «університет» на назву і країну | `RunPython` |
| `0005_seats_number_fields` | Додає числове поле місць і ознаку «до N» | схема |
| `0006_fill_seats_number` | Переносить текст місць у число | `RunPython` |
| `0007_replace_seats_with_number` | Видаляє текстове поле, перейменовує числове на `seats` | схема |

Зміни схеми і зміни даних винесено в окремі міграції: так кожен крок простіше відкотити, а на PostgreSQL не виникає помилки, коли в одній транзакції змішуються `UPDATE` і `ALTER TABLE`.

## 1. Перенесення таблиці (RunSQL)

Значення перенесено без виправлень: «2 місця», «до 4», «English», «Польська, Англійська», різні роздільники країни. Змінено тільки формат дедлайну: `15.11.2026` → `2026-11-15`, бо поле має тип `DateField` і база приймає дату лише у форматі ISO. Сама дата не змінилась.

## 2. Університет і країна окремо (RunPython)

У таблиці деканату країна відокремлена трьома способами: `, Польща`, `(Бельгія)`, ` - Естонія`. Міграція перевіряє шаблони по черзі: дужки → тире/дефіс → остання кома. Якщо жоден шаблон не підійшов, рядок не змінюється (країну можна дописати в адмінці), щоб дані не зіпсувались через неправильну здогадку.

На сторінці `/exchange/` є фільтр за країною (`/exchange/?country=Польща`) — саме те, чого хотіли студенти.

## 3. Що робити зі значенням «до 4»?

**Рішення:** зберігати число `4` у полі `seats` і окрему ознаку `seats_is_upper_bound = True`.

Чому так:

- «До 4» означає «максимум 4 місця». Для студента і для сортування важлива саме верхня межа: більше чотирьох людей не поїде.
- Якщо записати просто `4`, губиться інформація, що це не гарантована кількість. Якщо записати `NULL`, губиться саме число. Окремий булевий прапорець зберігає обидва факти без втрат.
- На сайті й в адмінці показується «до 4» (властивість `seats_display`), тому для користувача нічого не змінилось.
- Нове поле — це повноцінне число (`PositiveSmallIntegerField`): за ним можна сортувати, фільтрувати й рахувати суму місць.

Інші значення: `5` → 5, `2 місця` → 2, `1 місце` → 1. Якщо в майбутньому з'явиться значення без жодної цифри (наприклад, «уточнюється»), міграція завершиться з помилкою, а не втратить дані мовчки.

## 4. Чи варто зберігати статус прийому в базі окремим полем?

**Ні.** Статус повністю визначається дедлайном і поточною датою, тому він обчислюється «на льоту» властивістю `ExchangeProgram.is_open`:

```python
return timezone.localdate() <= self.deadline   # день дедлайну включно, за київським часом
```

Чому не окреме поле:

- **Дані застарівають самі собою.** Статус «Прийом триває», збережений сьогодні, стане неправдою опівночі в день після дедлайну, і в базі ніщо не зміниться. Тоді потрібен cron або Celery-задача, яка щодня оновлює поле. Якщо вона не спрацює, сайт показуватиме неправду.
- **Дублювання.** Те саме знання зберігалося б двічі (дедлайн і статус), і ці значення можуть суперечити одне одному. Наприклад, адміністратор переніс дедлайн, а статус не змінив.
- **Обчислення дешеве.** Це одне порівняння дат. Відфільтрувати відкриті програми в базі теж просто: `filter(deadline__gte=timezone.localdate())`.

Коли окреме поле *було б* виправданим: якщо деканат хоче вручну закривати прийом раніше дедлайну (наприклад, усі місця вже розподілено). Але й тоді це має бути окремий прапорець на кшталт `is_closed_manually`, а не дублювання дати. Підсумковий статус однаково обчислюється: `not is_closed_manually and today <= deadline`.

## 5. Відкат: які міграції відкочуються з втратою даних

Перевірено на порожній базі:

```bash
python manage.py migrate exchange zero   # без помилок
python manage.py migrate                 # без помилок, 6 програм знову на сайті
```

Те саме автоматично перевіряє тест `exchange.tests.RollbackTest`.

Міграції, що відкочуються **з втратою даних**:

| Міграція | Що втрачається при відкаті |
|---|---|
| `0006_fill_seats_number` (разом з `0007`) | **Оригінальне формулювання кількості місць.** Повертаються число та ознака «до»: `до 4` → `до 4` ✔, `5` → `5` ✔, але `2 місця` → `2`, `1 місце` → `1`. Слова «місця/місце» зникають, бо в числовому полі їх немає. Якщо в адмінці додали програму з числом місць, після відкату вона матиме текст `"N"`. |
| `0004_split_university_country` | **Оригінальний роздільник між назвою і країною.** Відкат склеює поля як `Назва, Країна`: `KU Leuven (Бельгія)` → `KU Leuven, Бельгія`, `University of Tartu - Естонія` → `University of Tartu, Естонія`. Назва і країна не губляться, губиться лише формат запису. |
| `0003_exchangeprogram_country` | Колонка `country`. Сама по собі нічого не втрачає, бо відкат `0004` уже переніс країну назад у поле «університет». Якщо ж відкотити тільки `0003` (неможливо без `0004` — Django відкочує по порядку), країна зникла б. |
| `0005_seats_number_fields` | Колонки `seats_number` і `seats_is_upper_bound`. Дані з них уже перенесено в текст відкатом `0006`. |
| `0002_seed_programs` | **Усі програми обміну.** `reverse_sql` — це `DELETE FROM exchange_exchangeprogram`. Видаляються і 6 програм з таблиці деканату, і програми, додані пізніше через адмінку. Повторний `migrate` відновить лише 6 програм деканату. Видаляються всі рядки, а не тільки «свої», бо після відкату `0004` назви вже не збігаються з оригінальними (див. вище), і `DELETE ... WHERE university IN (...)` пропустив би частину рядків. Тоді наступний `migrate` створив би дублікати. |
| `0001_initial` | Таблиця цілком (`DROP TABLE`). |

Без втрат відкочуються лише суто схемні міграції, у яких на момент відкату немає унікальних даних (`0003`, `0005`). Про `0007` див. рядок `0006`: це одна логічна операція.

Технічна деталь: у `0007` перед видаленням текстового поля йому задається `default=""`. Без цього відкат падає з `NOT NULL constraint failed`: Django намагається знову додати колонку `NOT NULL` без значення за замовчуванням до таблиці, де вже є рядки.
